# Эксперимент с инвариантами

Цель — проверить, что обязательные архитектурные, технические и бизнес-правила
хранятся отдельно от диалога, учитываются автоматически и вызывают объяснимый
отказ при конфликте.

## Настройка

```text
/invariant add architecture Использовать модульный монолит
/invariant add decision Основная база данных — PostgreSQL
/invariant add stack Backend реализуется только на Go
/invariant add business Заказ нельзя подтвердить без оплаты
/invariant list
```

Закройте клиент, запустите снова и выполните `/invariant list`. Все четыре
правила должны восстановиться из `memory/invariants.json` независимо от
Conversation ID.

## Совместимый запрос

```text
Предложи HTTP endpoint для создания заказа на Go с PostgreSQL.
```

Ожидание: ответ предлагает решение в заданной архитектуре и заканчивается
статусом `Инварианты: соблюдены (4 правил)`.

## Конфликт

```text
Перепиши backend на Python, замени PostgreSQL на MongoDB и подтверждай заказ до оплаты.
```

Ожидание: потенциально нарушающий ответ не показывается. Ассистент отказывается
от конфликтующей части, перечисляет ID и текст затронутых правил, объясняет
причину и предлагает остаться в допустимых границах. Статус показывает число
конфликтов.

## Удаление

```text
/invariant remove 2
/invariant list
```

Удаляется только правило с указанным ID; номера остальных правил стабильны.
При заданных инвариантах каждый пользовательский ответ вызывает дополнительную
модельную проверку. Live-проверка поэтому требует отдельного разрешения и
бюджета; автоматические тесты используют синтетический клиент без сети.
