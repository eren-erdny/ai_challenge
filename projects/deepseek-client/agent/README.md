# Компонент Agent

Пакет управляет циклом обработки запроса: проверяет ввод, готовит сообщения для
LLM, выполняет выбранный сценарий, проверяет ответы и возвращает результат.
Он не читает файлы, переменные окружения, stdin и не печатает в stdout.
В зависимостях пакета только стандартная библиотека Go.

## Подключение

Пример использования из другого Go-пакета этого приложения:

```go
import (
    "context"
    "os"

    "github.com/eren-erdny/ai_challenge/projects/deepseek-client/agent"
    "github.com/eren-erdny/ai_challenge/projects/deepseek-client/llm"
)

func ask(ctx context.Context, text string) (agent.Result, error) {
    client := llm.New(nil, map[string]string{
        "deepseek": os.Getenv("DEEPSEEK_API_KEY"),
    })
    runner := agent.New(client)
    return runner.Run(ctx, agent.Request{
        ConversationID: "dialog-1",
        Prompt:         text,
        Mode:           agent.Free,
        Target: agent.Target{
            Profile: "deepseek",
            BaseURL: "https://api.deepseek.com/v1",
            Model:   "deepseek-v4-flash",
            SendThinkingDisabled: true,
        },
        Temperature: 0.7,
        Strategy:    agent.Standard,
    })
}
```

`Agent` и HTTP-клиент можно создать один раз и использовать для нескольких
вызовов. В тестах вместо HTTP-клиента передаётся `agent.ClientFunc`.
Ключи принадлежат клиенту; в `Request`, `Result` и метриках полей с ключами нет.

## Контракт

- `Request`: исходный текст, идентификатор диалога, режим, настройки и модели.
- `Result.Responses`: ответы с моделью, метриками, оценкой стоимости и проверками.
- `Result.Analysis`: ответ судьи, если выбран benchmark и анализ завершился.
- `Result.Last()`: последний успешный вызов, включая судью.
- `error`: ошибка ввода, модели, судьи или отмена. Проверяется через `errors.Is`.

При ошибке второй модели первый ответ остаётся в `Responses`. При ошибке судьи
сохраняются все три ответа. Вызывающий код должен обработать и результат, и ошибку.
Провал проверки формата возвращается в `Validation.Passed`, а не как ошибка API.
Автоматических повторов и исправления ответа нет.

## Сценарии и политики

| Режим | Выполнение |
| --- | --- |
| `Free` | Один ответ, без response-control; выбранная стратегия сохраняется |
| `Controlled` | Один ответ с форматом, лимитами и локальной проверкой |
| `Compare` | Ответ без ограничений, затем с ограничениями |
| `TemperatureBenchmark` | Температуры 0, 1.2, 2 с прежними компактными инструкциями, затем судья |
| `ModelBenchmark` | Три цели из `Targets` с одинаковыми настройками; судья использует вторую цель |

В приложении список `Targets` формируется из профилей DeepSeek и Ollama; вторым
участником является DeepSeek Pro. Сам пакет агента не ищет профили в конфигурации.

Input policy проверяет непустой текст, модель, режим, температуру, стратегию и
настройки ограничений до вызова клиента. Она формирует системные инструкции и
сообщение пользователя. Списки целей и stop sequences копируются на запуск.

Output policy выполняет существующие проверки формата, длины и завершения для
ответов с включённым контролем. В benchmark температуры и служебных вызовах
судьи сохраняются прежние инструкции и лимиты без локальной проверки формата.
Судья получает исходную задачу, ответы и метрики. Оценка стоимости использует
существующий справочник тарифов и может отличаться от фактического списания.

## Интерфейс и отмена

TUI и CLI используют `agent_adapter.go`: он переводит настройки приложения в
запрос агента, разрешает ключи провайдеров и передаёт результат функциям вывода.
Агент возвращает данные без оформления терминала.

`context.Context` передаётся от интерфейса до `http.NewRequestWithContext`.
Выход из TUI отменяет активную работу; Ctrl+C отменяет HTTP-вызов в CLI.
После отмены новые шаги сценария не запускаются.

## Память

`agent.NewWithHistory(client, store)` подключает интерфейс `HistoryStore` с
методами `Load` и `Save`. Пакет `history` реализует его через JSON-файлы.
`agent.New(client)` сохраняет прежнее поведение без памяти.

В режимах `free` и `controlled` агент загружает историю по `ConversationID`,
добавляет её после актуальной системной инструкции и перед новым вопросом.
После успешного ответа сохраняет пару `user`/`assistant`. При ошибке сохранения
возвращает полученный ответ вместе с ошибкой, не скрывая потерю сохранения.
Системные инструкции и ключи не сохраняются. Режимы сравнения и benchmark
не читают и не изменяют историю обычного диалога.

Приложение восстанавливает последний выбранный ID из `conversations/.active.json`
и показывает его переписку при запуске. JSON лежит в `conversations/<ID>.json` рядом с
пользовательским конфигом, вне репозитория. Файл содержит версию схемы,
идентификатор диалога и массив `messages`.

Запись выполняется во временный файл с синхронизацией и заменой основного.
При ошибке замены старый файл не удаляется. Повреждённая история вызывает
явную ошибку, а не молчаливый запуск пустого диалога.

Используйте один запущенный клиент на одну папку истории: параллельная запись
из нескольких процессов не поддерживается. История хранится открытым текстом;
на Unix новые папки имеют права 0700, файлы 0600, на Windows действуют ACL
пользовательской папки. При смене профиля вся история отправляется новому
провайдеру. Не вводите секреты в переписку.

Автоматического сокращения контекста пока нет: длинная история увеличивает
число входных токенов и может превысить контекстное окно модели. Файл больше
16 MiB отклоняется с ошибкой. `/new` создаёт новый диалог со случайным ID без
удаления предыдущего. `/conversation ID` загружает существующий диалог; ID
проверяется, чтобы исключить выход за пределы папки. `/conversation` показывает
текущий ID, он также выводится в терминал при выходе. `/clear` очищает только
экран, но не память. Режим и настройки модели при переключении сохраняются.

`history.JSON` предоставляет управление диалогами отдельно от интерфейса агента
`HistoryStore`: `Active`, `NewConversation`, `Select`. При первом запуске после
обновления выбирается прежний `default`, поэтому существующая история не теряется.
При ошибке загрузки или записи выбора активный диалог в интерфейсе не меняется.

## Проверка

`Response.Tokens` содержит раздельные оценки нового вопроса, истории и инструкций.
`LastUserMessageEstimate` означает только последнее сообщение пользователя,
а `InputEstimate` и фактический `InputActual` (`prompt_tokens`) — текущий запрос целиком.
История является частью полного входа, а не дополнительным расходом поверх него.

Также отчёт содержит оценки накладных расходов и ответа,
а также фактические вход/выход/сумму из API usage.
`WithTokenCounter` позволяет внедрить счётчик для конкретного токенизатора;
встроенный `ApproximateCounter` является только эвристикой. `Target.ContextWindow`
и `Target.MaxOutputTokens` задают локальный бюджет. При превышении возвращаются
`ContextLimitError` и `Result.Failed` с метриками без вызова клиента.
При ошибке API `Result.Failed` также содержит оценки подготовленного запроса.
Контекст не сокращается автоматически. Измеренный usage не выводится из длины
текста; неизвестная стоимость не подменяется нулевой.

Из корня репозитория:

```powershell
go test ./projects/deepseek-client/...
```

Тесты покрывают все сценарии, политики, частичные результаты, изоляцию настроек,
отмену и прохождение запроса через локальный HTTP-сервер. Тест
`TestConversationSurvivesProcessRestart` запускает CLI-сессию в двух отдельных
процессах и проверяет восстановление истории в HTTP-запросе и интерфейсе.
Облачные API не нужны.

## Компрессия истории

`CompressionStore` расширяет хранилище отдельными операциями для summary и
учёта его API-вызовов. `Agent.Compress` сохраняет полную историю, создаёт новое
структурированное summary старой части и атомарно публикует его только после
проверки ответа и неизменности исходной истории. `Run` подставляет summary вместо
покрытых сообщений. `Request.Compression` задаёт число свежих сообщений и
автоматическое сжатие на 80% настроенного контекстного окна.

Нулевая конфигурация означает `keep_last=10` и включённое автосжатие. Оно
фактически работает только при ненулевом `Target.ContextWindow`. Реализация
хранилища обязана отвергать устаревшую запись summary, если сообщения или версия
изменились между чтением и сохранением.

## Стратегии памяти

`Request.Compression.Strategy` выбирает `full`, `summary`, `sliding`, `facts` или
`branching`. Нулевое значение сохраняет прежний режим `summary`. Sliding window
строится через `RecentHistory` и не удаляет сообщения из `HistoryStore`.

Facts используют отдельный `FactStore`. После сохранения каждого успешного хода
`RefreshFacts` извлекает из новых user-сообщений полную key-value карту. Перед
следующим ответом незавершённое обновление повторяется. В запрос попадают facts
и свежий хвост. Расход экстрактора сохраняется отдельно и входит в общую
статистику.

Branching реализуется хранилищем через `BranchStore`: checkpoint фиксирует снимок
активной истории, две новые ветки могут начать работу с одного снимка, а Load и
SaveTurn относятся к активной ветке. Агенту не требуется знать структуру JSON
веток; в режиме branching он получает от HistoryStore полную активную историю.
