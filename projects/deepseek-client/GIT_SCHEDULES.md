# Периодические Git-сводки через MCP

Git MCP выполняет задания сам, даже если клиент отключён. Планировщик не вызывает
LLM: он собирает факты о серверном клоне и формирует агрегат. Для работы 24/7
процесс должен оставаться запущенным, например через systemd из [GIT_MCP.md](GIT_MCP.md).

## Что добавлено

| Инструмент | Назначение |
| --- | --- |
| `git_summary_schedule` | Сохранить отложенное или периодическое задание |
| `git_summary_list` | Показать все расписания и агрегированные результаты |
| `git_summary_get` | Получить сводку конкретного задания |
| `git_summary_cancel` | Остановить будущие выполнения, сохранив результаты |

Аргументы создания:

```json
{"id":"minute-review","delay_seconds":5,"interval_seconds":60,"write_file":true}
```

`id` — уникальная строка до 64 букв/цифр/символов `_` и `-`.
Первый запуск будет через `delay_seconds` (от 1 до 604800 секунд).
`interval_seconds` — интервал от завершения предыдущего запуска (от 10 до 604800
секунд); `0` или отсутствие поля означает однократное выполнение.
Повтор идентичного создания возвращает существующее задание; он не сбрасывает
историю и не возобновляет отменённое задание. Для нового задания выберите новый ID.
`write_file` необязателен и по умолчанию равен `false`. При `true` после каждого
запуска сервер обновляет читаемый `summary-<id>.txt` в `--data-dir`. Путь
возвращается в поле `summary_file`; клиент не задаёт произвольный путь.
При перезапуске файл восстанавливается из сохранённого JSON, а при отмене в нём
обновляется `active=false`. Ошибка записи файла останавливает планировщик.
На VPS файл будет на VPS, а при локальном запуске — на этом компьютере.

## Запуск сервера

Данные храните вне наблюдаемого клона, чтобы JSON-сводки не меняли его статус:

```bash
"$HOME/git-mcp" --repo "$HOME/ai_challenge" --data-dir "$HOME/.local/state/git-mcp"
```

Требования к токену и SSH-туннелю те же, что в [инструкции развёртывания](GIT_MCP.md).
Добавьте `--data-dir /home/USER/.local/state/git-mcp` в `ExecStart` systemd-сервиса
и перезапустите сервис после замены бинарника. Без флага используется
каталог пользовательской конфигурации `git-mcp/<хэш пути репозитория>`.
Старые запущенные процессы не получают новые инструменты автоматически.

В указанном каталоге находятся `schedules.json` и `scheduler.lock`. JSON хранит
расписания, время следующего запуска, результаты и счётчики. Запись использует
временный файл, sync и rename. ОС-блокировка запрещает одновременную работу двух
серверов с одним каталогом и освобождается также после аварийного завершения.
Наличие файла `scheduler.lock` само по себе не означает активную блокировку.
Каталог предназначен для локального диска одного сервера, не сетевого общего FS.
Не редактируйте JSON, пока процесс работает. Повреждённый файл или несовпадение
пути репозитория приводит к ошибке запуска без перезаписи данных.

## Проверка без модели

После установки `GIT_MCP_URL` и `GIT_MCP_TOKEN` в PowerShell 7:

```powershell
go run ./projects/deepseek-client --mcp-list
go run ./projects/deepseek-client --mcp-call git_summary_schedule '{"id":"minute-review","delay_seconds":5,"interval_seconds":60,"write_file":true}'
```

Клиент завершится, а сервер продолжит работу. Через несколько секунд:

```powershell
go run ./projects/deepseek-client --mcp-call git_summary_get '{"id":"minute-review"}'
go run ./projects/deepseek-client --mcp-call git_summary_list '{}'
```

В результате появятся `runs`, `failures`, `latest` и `summary`. После второго
периода `runs` увеличится. Остановить задание:

```powershell
go run ./projects/deepseek-client --mcp-call git_summary_cancel '{"id":"minute-review"}'
```

Однократная отложенная сводка:

```powershell
go run ./projects/deepseek-client --mcp-call git_summary_schedule '{"id":"once-review","delay_seconds":10,"interval_seconds":0}'
```

## Использование агентом

Запустите приложение с теми же переменными окружения, затем `/mode free` и
`/tools on`. Пример запроса:

> На сервере git создай задание minute-review: первая сводка через
> 5 секунд, затем каждые 60 секунд. Записывай сводку в файл и покажи его путь.

Позже:

> На сервере git получи накопленную сводку minute-review и объясни её.

Агент получает схему инструментов, вызывает MCP и использует результат в ответе.
Диалог с моделью использует обычный API-профиль, но фоновый планировщик работает
независимо от модели, клиента и API-ключей.

## Куда приходят сводки

Если задано `write_file=true`, обновляемый текстовый файл содержит агрегат,
границы наблюдений, активность задания и время следующего запуска. Основной
`schedules.json` остаётся источником сохранённого состояния. Файл сводки
находится в том же защищённом каталоге данных вне наблюдаемого Git-клона.

Локальная проверка домашки 18: модель сама выбрала инструменты по описанию задачи,
создала расписание, прочитала агрегат и отменила будущие запуски. JSON сохранился;
сбор продолжался без клиента и после перезапуска сервера. Получено 6 наблюдений
без ошибок. См. [результаты проверки](../../raw/project/2026-09-27-hw18-scheduler-live.md).
Это короткий локальный прогон, не проверка суток работы. Демонстрационный сервер
после записи остановлен; VPS и постоянный запуск отложены.

После каждого сохранённого выполнения сервер сам печатает `[git-summary]` с
агрегатом в stderr. При systemd это журнал:

```sh
journalctl --user -u git-mcp -f
```

Результаты доступны через MCP даже после перезапуска. **Автоматических сообщений
в закрытый чат, Telegram или email нет**: агент читает их по запросу пользователя.
Для push-уведомлений нужен отдельный канал доставки. Поэтому «24/7» здесь означает
постоянно работающий сервер-планировщик, а не бесконечные обращения к LLM.

## Что агрегируется и как обрабатываются сбои

- Снимок: ветка, HEAD, число изменённых tracked-записей, untracked-записей и
  конфликтов. Каталог untracked может считаться одной записью. Содержимое diff
  и файлов в JSON не сохраняется.
- За всё время: число запусков и ошибок. По последним 32 снимкам: число грязных
  состояний, наблюдавшихся смен HEAD и максимальное число конфликтов, границы
  окна и последний результат. Смены HEAD — не количество новых коммитов.
- Хранится максимум 16 расписаний (включая завершённые/отменённые) и 32 снимка
  на расписание. Удаление/редактирование расписаний через MCP пока не добавлено.
- Проверка готовности — раз в секунду, исполнение последовательное. Сбор имеет
  таймаут 8 секунд. Точная секунда старта не гарантируется при нагрузке.
- После простоя каждое просроченное активное задание выполняется один раз;
  пропущенные состояния не выдумываются, затем отсчитывается новый интервал.
- Ошибка Git сохраняется и учитывается в агрегате; периодическое задание
  продолжает работать. Ошибка сохранения JSON останавливает сервис с ошибкой,
  чтобы не выдавать несохранённые результаты за успешные.
- Отмена ждёт уже начатого сбора, затем запрещает следующие. При штатной
  остановке незавершённый сбор будет повторён после запуска. При аварии между
  сбором и сохранением возможен повтор чтения; гарантии exactly-once для журнала нет.
- Сервер не делает fetch: наблюдает только изменения собственного клона. Для
  наблюдения за изменениями на GitHub потребуется отдельно добавить сбор с fetch.

Проверка реализации:

```powershell
go test ./projects/deepseek-client/gitmcp -v
```

Интеграционный тест создаёт расписание через HTTP MCP из цикла агента со сценарной
моделью, отключает клиента, ждёт реального таймера, получает результат и проверяет
его после открытия JSON заново. Другие тесты проверяют периодичность, пропуски,
агрегацию, отмену, лимиты хранения, блокировку и ошибки сохранения. Внешних API нет.
