# Автоматический MCP-пайплайн: поиск → сводка → файл

Три отдельных инструмента зарегистрированы на Git MCP-сервере:

| Инструмент | Вход | Выход |
| --- | --- | --- |
| `git_search_commits` | `query`, необязательный `limit` | `query`, массив `commits` с hash и subject |
| `git_summarize_commits` | Полный результат поиска | `query`, `commit_count`, `categories`, `markdown` |
| `git_save_report` | Полный результат сводки | `file`, `bytes`, `sha256` |

Первый шаг получает реальные данные локального серверного Git-клона. Второй
формирует детерминированную Markdown-сводку: количество найденных коммитов,
категории `feat`, `fix`, `docs`, `test`, `other` и список заголовков с хэшами.
Это сводка по правилам, без обращения к LLM. Третий сохраняет переданный Markdown
без изменений в `<data-dir>/reports/git-summary-<случайный ID>.md` на сервере.

## Автоматический запуск одной командой

Обновите бинарник Git MCP и перезапустите сервер по [инструкции](GIT_MCP.md).
Подключение использует `GIT_MCP_URL` и `GIT_MCP_TOKEN`, как в предыдущих заданиях.
Из корня репозитория:

```powershell
go run ./projects/deepseek-client --mcp-list
go run ./projects/deepseek-client --mcp-pipeline fix
```

В списке теперь 11 инструментов. Команда пайплайна автоматически выполняет три
последовательных `tools/call` через HTTP MCP. Не нужно вручную копировать JSON:
каждый структурированный ответ становится входом следующего вызова без правок.
CLI использует максимум 20 совпадений. Для поиска по всей доступной выборке
последних коммитов передайте пустую строку в PowerShell 7:

```powershell
go run ./projects/deepseek-client --mcp-pipeline ''
```

Результат — JSON со списком завершённых `steps`, сводкой `summary` и данными
сохранённого файла `saved`. Клиент проверяет query, число коммитов, размер и
SHA-256 сохранённого Markdown. `saved.file` — путь **на сервере**, а не на
компьютере клиента. Markdown также присутствует в ответе команды.
Запуск этой команды не использует модель или внешний API.

## Запуск агентом

В обычном чате после `/mode free` и `/tools on`:

> Найди коммиты с fix, сделай сводку и сохрани отчёт. Используй последовательно
> git_search_commits, git_summarize_commits и git_save_report.

Инструменты доступны общему циклу агента. В инструкциях указано передавать
полный результат между шагами, прекращать цепочку при ошибке и сообщать об
успехе только после сохранения. Диалог использует настроенную модель; её
поведение зависит от поддержки tool calling. CLI обеспечивает фиксированную
цепочку без выбора действий моделью.

## Границы

- Поиск идёт по сообщениям коммитов, достижимых из текущего HEAD серверного
  клона, как буквальная подстрока без учёта регистра; fetch не выполняется.
  `limit` по умолчанию 20, диапазон 1–50. Query — до 200 байт, без переводов
  строк и NUL. В результате сохраняются только хэши и заголовки коммитов.
- Пустой результат корректен: формируется и сохраняется отчёт «No matching
  commits». Если в клоне нет первого коммита, Git возвращает ошибку.
- Summarize не делает семантический анализ diff и не утверждает, что выборка
  содержит все коммиты репозитория. Категории определяются по Conventional
  Commits-префиксам; остальные заголовки попадают в `other`.
- На ошибке цепочка прерывается. Автоматических повторов сохранения нет;
  повтор запуска создаёт новый отчёт. Ошибка ответа после успешной записи
  может означать, что файл уже появился на сервере.
- Путь файла модель не задаёт. Запись идёт через закреплённый дескриптор папки,
  с новым случайным именем и без перезаписи. Максимум Markdown — 256 KiB.
  Папка reports не должна быть символической ссылкой. Репозиторий не меняется.
- Отчёты сохраняются открытым текстом с правами 0600, без автоматической очистки.
  Токен MCP даёт право создавать их; следите за свободным местом при длительной
  эксплуатации. `git_save_report` сохраняет переданный текст, но не удостоверяет
  его происхождение из реального Git-поиска при прямом ручном вызове.

## Проверка

```powershell
go test ./projects/deepseek-client/mcppipeline -v
```

Тест создаёт настоящий временный Git-клон и HTTP MCP-сервер. Проверяются порядок
трёх вызовов, точное совпадение данных на границах шагов, категории, сохранённые
байты и отсутствие перезаписи. Проверяются пустой поиск и остановка при ошибке
каждого шага. Отдельный тест проводит ту же цепочку через цикл агента со сценарной
моделью. Внешние API, настоящий LLM и VPS в этих тестах не используются.
