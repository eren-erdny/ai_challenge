# Несколько MCP-серверов

Основной агент теперь подключает одновременно встроенный GitHub MCP (stdio)
и Git MCP (HTTP), если задан GIT_MCP_URL. Инструменты публикуются как
`github__github_get_repository`, `git__git_status` и т. д.
Локальные файловые инструменты сохраняют свои имена.

## Запуск

Поднимите Git MCP и SSH-туннель по [инструкции](GIT_MCP.md).
Из корня репозитория в PowerShell:

```powershell
$env:GIT_MCP_URL = 'http://127.0.0.1:18080/mcp'
# GIT_MCP_TOKEN должен содержать токен вашего сервера.
go run ./projects/deepseek-client --mcp-multi-list
go run ./projects/deepseek-client
```

Для другого набора серверов задайте MCP_SERVERS_FILE — путь к JSON по образцу
[mcp-servers.example.json](mcp-servers.example.json). Файл полностью заменяет
набор по умолчанию. Поддерживаются builtin-github и http; токен передаётся
через переменную окружения, указанную в token_env, не через JSON.
После изменения конфигурации перезапустите приложение.

Допускается от 1 до 8 серверов. Имена уникальны, состоят из строчных латинских
букв, цифр и дефисов, начинаются с буквы и не длиннее 16 символов.
Полное имя инструмента ограничено 64 символами. Одинаковые исходные имена
на разных серверах не конфликтуют благодаря префиксу.

## Длинный сценарий

В диалоге включите `/mode free` и `/tools on`, затем задайте цель, не называя
инструменты и их порядок:

> Подготовь отчёт: покажи сведения о публичном golang/go и отдельно о
> серверном Git-клоне, включая его состояние и сводку коммитов с `fix`.
> Сохрани сводку в файл и сообщи путь. Не считай, что это один репозиторий.

Допустимый порядок не фиксирован. Для такого результата агенту могут
понадобиться инструменты обоих серверов, например:

1. github__github_get_repository
2. git__git_status
3. git__git_branches
4. git__git_search_commits
5. git__git_summarize_commits
6. git__git_save_report

Достаточно, чтобы необходимые вызовы действительно прошли через оба сервера,
поиск предшествовал сводке, а сохранение получило настоящую сводку. Независимые
шаги могут идти в другом порядке. Модель выбирает каждый вызов из общего
списка по описанию и предыдущим результатам; системный промпт не предписывает
цепочку. Приложение маршрутизирует точное имя на нужную сессию и передаёт
исходное имя серверу. Результат возвращается модели с соответствующим
tool_call_id. Файл хранится на Git MCP сервере, вне клона.

Для диагностики без модели:

```powershell
go run ./projects/deepseek-client --mcp-multi-call git__git_status '{}'
```

Старые --mcp-list, --mcp-call и --mcp-pipeline сохранены как односерверные
команды без префиксов; они не используют MCP_SERVERS_FILE.

## Ошибки, безопасность и проверка

Подключение строгое: ошибка любого сервера прерывает запуск и закрывает уже
открытые сессии. Таймаут подключения — 10 секунд на сервер; MCP-вызова —
20 секунд. Неизвестное имя отклоняется, ошибка не приводит к переносу
операции на другой сервер. HTTP разрешён только для literal loopback;
для внешнего адреса нужен HTTPS. Существующая проверка Bearer-токена
сохраняется. Конфиг не позволяет запускать произвольные команды.

Цикл ограничен 8 раундами модели и 32 вызовами; последний раунд — ответ
без инструментов. Это длинный ограниченный флоу, не бесконечная работа.
Список инструментов не обращается к GitHub API; вызов метаданных обращается.
Работа диалога с настоящей моделью расходует её API-бюджет.

Проверка из projects/deepseek-client:

```powershell
go test ./...
go vet ./...
go test ./mcppipeline -run TestRoutesLongFlowAcrossServersWithScriptedModel -v
```

Интеграционный тест использует два настоящих HTTP MCP-соединения, временный
Git-репозиторий и сохранение отчёта. Его сценарная модель задаёт шесть вызовов;
тест проверяет маршрутизацию, порядок, корреляцию результатов и точную передачу
JSON. Он не доказывает самостоятельный выбор DeepSeek. Отдельный unit-тест
проверяет, что системный промпт не задаёт порядок Git-инструментов. Остальные
unit-тесты покрывают одинаковые имена на разных серверах, отсутствие failover,
закрытие сессий и конфигурацию.
