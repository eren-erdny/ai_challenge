# Эксперимент режима task

Цель — проверить явные контролируемые переходы, обязательное утверждение плана,
валидацию перед завершением, паузу и продолжение без повторного описания задачи.
Ручных команд `/task` нет: намерение выражается обычным сообщением, а переход
возвращается моделью и независимо проверяется агентом.

## Основной сценарий

```text
/new
/mode task
Подготовь и проверь HTTP endpoint состояния.
Продолжай.
Утверждаю план, начинай реализацию.
Поставь задачу на паузу: нужно согласовать контракт.
Что сейчас происходит с задачей?
Возобнови задачу.
Продолжай.
```

После первого запроса состояние должно начаться с `planning`. Первое
«Продолжай» не утверждает план: попытка перейти к реализации должна остаться в
`planning` либо быть заменена объяснением с просьбой явно утвердить план. После
«Утверждаю план» разрешается только переход в `execution`.

Каждый ответ завершается строками вида
`[transition:advance разрешён] planning → execution` и
`[task:execution] шаг → ожидаемое действие`. Этап может остаться прежним или
перейти только на следующий: `planning → execution → validation → done`.
`execution → validation` требует свидетельства завершённой реализации, а
`validation → done` — свидетельства успешной проверки. Проваленная проверка
оставляет задачу в `validation`.

Если выбранная модель иногда отвечает обычным текстом вместо внутреннего JSON,
клиент должен автоматически выполнить один repair-вызов и показать строку
`[task] Формат ответа модели восстановлен дополнительным вызовом`. После неё
должны выводиться обычные transition и task строки. Такой ход расходует два
модельных вызова; их usage суммируется в `/status last`.

На паузе состояние сохраняет этап и показывает `(пауза)`. Ответ, снимающий
паузу, ещё не может одновременно перейти на следующий этап. Следующее
«Продолжай» использует сохранённые цель и прогресс.

## Негативные проверки

Попросите сразу перейти к валидации на этапе `planning` и сразу объявить задачу
готовой на этапе `execution`. В обоих случаях прежний этап должен сохраниться,
в ответе должна быть названа пропущенная предпосылка, а текст действия из
отклонённого предложения модели не должен становиться пользовательским ответом.

На этапе `validation` попросите завершить задачу без запуска проверки. Переход
в `done` должен быть отклонён из-за отсутствия свидетельства успешной
валидации.

## Проверка восстановления

Закройте клиент после постановки задачи на паузу, снова запустите его и введите:

```text
/mode task
Продолжай.
```

Ожидание: состояние загружается из `memory/tasks/<ConversationID>.json`; цель
пересказывать не нужно. Возобновление оставляет тот же этап. После `done` можно
обычным сообщением дать другую задачу, и она должна начать отдельный цикл с
`planning`.

Автоматические тесты проверяют создание задачи, явное утверждение плана,
объяснимый отказ на обычное «Продолжай», свидетельства для переходов, запрет
скачков, сохранение между экземплярами хранилища, паузу и возобновление на том
же этапе, изоляцию Conversation ID, защиту от устаревшей записи и строгий
JSON-протокол. Live API для этих проверок не нужен.
